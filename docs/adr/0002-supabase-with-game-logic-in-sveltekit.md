# Supabase for data, auth and realtime; game logic runs in SvelteKit server routes

We use Supabase (Postgres, Auth, Realtime) as the only backend service, next to SvelteKit on Vercel. Supabase has no process that holds a game, so the pure TypeScript state machine runs in SvelteKit server routes: load the game, apply the command, save it back. Postgres stores the state without knowing its shape. The rules live in one place, the same module the scenario builder drives.

- **Realtime is a nudge, not a payload.** After every change the server broadcasts only `{gameId, version}` on a public channel per game. Each phone then fetches the game state **redacted for its seat** (no year before placement; card text only for the reader) and decides for itself what to render. No secret travels over a realtime channel, and reconnecting or reloading is the same refetch. This costs one extra round trip per change, which a turn-based game can afford.
- **The game state is one jsonb value per game, with a version.** It is created when the host starts the game, with the deck snapshotted into it, so a card edited mid-game can't change a game in progress. Each save checks the version it loaded (`where version = <loaded>`); a conflict means the server reloads and retries the command, and a command based on an old version is rejected so the phone refetches. Joining before the start writes its own rows rather than the jsonb value, so simultaneous joins can't overwrite each other. Seating itself is decided elsewhere.
- **Identity:** each phone signs in anonymously, and a player's seat belongs to that user. An anonymous user can later be linked to a real account, which is the path to player accounts. Admins sign in with Google OAuth. Access comes from a `user_roles` table (`admin`, `editor`), surfaced as a claim by Supabase's Custom Access Token hook.
- **The browser never touches tables.** It uses `supabase-js` only for its session and the nudge channel. All reads and writes go through SvelteKit server routes, and RLS denies direct table access as defence in depth.
- **Schema and audit live in SQL.** Supabase CLI migrations are the single source of truth, with generated types, accessed through `supabase-js`; there is no ORM. The admin audit log is written by database triggers on cards and categories, because Supabase audits auth events only. If several statements must succeed or fail together, that is a Postgres function called with `.rpc()`.
- **Ops:** a "When Then" organisation with one hosted Free project (production), with collaborators added as Developers; local development uses the Supabase CLI. Free projects pause after a week without activity. We accept that, with a scheduled job that runs a real query every few days; Pro ($25/month) is the escape hatch.

## Considered options

- **Convex + Better Auth** (ranked first by the research): logic runs next to the state, and per-caller reactive queries give per-role views for free. Rejected in favour of Supabase, which the team already knows well, with the most mature auth (roles, anonymous sign-in) and a relational store for cards and admin.
- **Cloudflare Durable Objects via PartyServer:** the purest room server, but it is a second platform with no auth or admin story.
- **Private per-player Broadcast topics gated by RLS on `realtime.messages`:** rejected for the nudge-and-refetch approach; it puts secrets on channels and depends on per-connection policy caching.
- **Game logic in Postgres functions or Edge Functions:** rejected because it splits the rules from the TypeScript state machine, or adds a second runtime and deploy target.
- **Normalised game tables** (timelines, plays, steals): rejected because they repeat the state machine's shape in SQL, mapping code and migrations. If analytics need per-play data, an append-only command log can be added later.
- **Pessimistic locking** (`select … for update` in a transaction over a direct connection): rejected because it needs a direct Postgres connection and holds a row lock while application code runs; the version check gives the same safety over `supabase-js`.
- **Drizzle ORM:** rejected because RLS, the role hook and audit triggers are SQL anyway, and two migration tools on one database invite drift.
