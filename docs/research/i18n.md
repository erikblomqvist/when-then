# i18n for the SvelteKit UI and translated card content

Research for [#6](https://github.com/erikblomqvist/when-then/issues/6). Checked 2026-10-20 against official docs, package registries and repos. Versions quoted are from the npm registry on that date.

## Answer in brief

- **UI strings: use Paraglide JS v2** (`@inlang/paraglide-js`, 2.29.1, published 2026-10-19). It is the integration the Svelte CLI installs (`vp dlx sv add paraglide`), it compiles messages to typed, tree-shakable functions, and it has a documented SvelteKit setup that covers SSR.
- **Locale per player, not per URL.** Every phone opens the same join link or QR code, so the locale should not live in the URL. Configure `strategy: ['cookie', 'preferredLanguage', 'baseLocale']`. Each phone then gets its browser language on first visit and keeps any manual choice in a cookie that SSR can read.
- **Card content stays out of Paraglide.** Paraglide is compiled at build time, so it is for fixed UI strings only. Cards and categories are admin-edited data and need a database pattern. The recommended pattern is a **language-neutral `card` row plus a `card_translation` table** (option C below). A JSONB column (option B) is an acceptable simpler fallback.

**Why Paraglide:** it is the only option that is first-party in the Svelte tooling, fully typed out of the box, SSR-safe by design and actively maintained. It also has a CLI for machine translation and a missing-translation check, which suits the v1 Swedish and English requirement and makes adding Norwegian later cheap. wuchale's keyless approach is appealing, but the project is still pre-1.0. sveltekit-i18n is a credible runtime alternative if lazily loaded, route-scoped JSON is ever wanted, but that matters little with only 2–3 locales.

## 2. Paraglide in SvelteKit: what matters for this game

### Setup ([SvelteKit guide](https://paraglidejs.com/sveltekit))

- `vp dlx sv add paraglide="languageTags:sv,en"` sets up the inlang project, the Vite plugin, the `reroute` and `handle` hooks, and `lang`/`dir` in `app.html` ([Svelte CLI docs](https://svelte.dev/docs/cli/paraglide)).
- In `vite.config`, add `paraglideVitePlugin({ project: './project.inlang', outdir: './src/lib/paraglide', strategy: [...] })`.
- In `src/hooks.server.ts`, add `paraglideMiddleware(event.request, ({ request, locale }) => resolve(...))` and fill `%lang%` in `transformPageChunk`. The guide notes that SvelteKit 3 makes `event.request` readonly, so pass a copied event. SvelteKit is currently at 3.1.0.
- `src/hooks.ts` `reroute` using `deLocalizeUrl` is needed only with the `url` strategy. Without it, the hook can be dropped.

### Locale detection and switching per player ([Strategy docs](https://paraglidejs.com/strategy))

- Strategies are tried in order, and "the first strategy that successfully returns a locale will be used." The built-in strategies are `cookie`, `baseLocale`, `globalVariable`, `preferredLanguage` (`navigator.languages` on the client, `Accept-Language` on the server), `localStorage` (browser-only) and `url`. Custom `custom-<name>` strategies can be added through `defineCustomClientStrategy` and `defineCustomServerStrategy`.
- **Recommended:** `['cookie', 'preferredLanguage', 'baseLocale']`, with `baseLocale` set to `sv` or `en` (product decision).
  - **Why no `url`:** the host shares one link or QR code, and players at the same table may want different languages. Locale-prefixed URLs would force the host's language on everyone.
  - **Why `cookie` and not `localStorage`:** "the initial document request cannot read `localStorage`". A cookie keeps SSR output in the right language on the first paint.
- `setLocale()` by default "performs a full document navigation or reload". `setLocale(locale, { reload: false })` is a "deliberately narrow escape hatch" for fully client-rendered surfaces that don't use the `url` strategy. Implication: put the language switcher on the start, join and lobby screens, where a reload is cheap. If switching mid-game is wanted, either rely on v1 reconnect-to-own-seat to survive the reload, or make the game route CSR-only and use `reload: false`.
- **Norwegian later:** browsers may report `nb`, `nn` or `no`. `preferredLanguage` matches exact tags first and then base codes, so the locale tag chosen (likely `nb`) may need a small custom strategy that aliases `no`→`nb`.

### Plurals and formatting ([Variants](https://paraglidejs.com/variants))

Plurals use `Intl.PluralRules` through declarations and selectors (`local countPlural = count: plural`), which covers things like "1 poäng" vs "3 poäng". Number and date formatting is documented separately. For years, plain numbers are enough.

### SSR, PWA and Vercel

- The server middleware uses AsyncLocalStorage, so concurrent requests don't leak locales. The guide says to keep it enabled on Vercel and edge runtimes. `disableAsyncLocalStorage` is only for runtimes that isolate each request.
- Caveat: calling messages on the server outside load functions or hooks (for example in a realtime/WebSocket handler) has no request to read the locale from. **Implication: the server should send codes and enums (event types, error codes), and the client renders them with `m.*()`.** Card text is the exception: it is content, delivered in the game's card language (see §3).
- PWA: compiled messages are ordinary JS modules in the build output, so they are precached like any other asset. SvelteKit 3 exposes `immutable`, `assets` and `prerendered` from `$app/manifest` and `version` from `$app/env` for versioned caches ([Service workers](https://svelte.dev/docs/kit/service-workers)). Paraglide's docs don't address service workers, and nothing locale-specific is needed when the URL carries no locale.

### Translator workflow

Messages are kept as `messages/sv.json` and `messages/en.json` in git. Non-developers can edit them in Fink. `vp dlx @inlang/cli machine translate --targetLocales nb` bootstraps a new locale. `vp dlx @inlang/cli check --missing-translations` exits with 1 on gaps, so it can gate CI ([inlang CLI](https://inlang.com/m/2qj2w8pu/app-inlang-cli)).

## 3. Translatable card content: data-model patterns

Context from the map (#2): cards and categories are admin-edited, the admin has AI "translate" in v1, multilingual cards are a later feature that v1 must not preclude, and dealing should avoid repeats within a game and ideally across games. Note that `GLOSSARY.md` currently defines a Card as having "its language". Whichever pattern is chosen should update that definition.

Cards are read aloud by the reader to the whole table, so the useful unit is a **card language per game**, not per player. The deck is filtered to cards available in that language, independently of each phone's UI locale.

### A. Per-language rows (one `card` row per language)

`card(id, locale, text, year, category_id, …)`, optionally with a `translation_group_id`.

- Pros: simplest, and it matches the current glossary literally.
- Cons: year, category and source are duplicated and can drift between languages. Without a group id, "don't repeat across games" breaks because the same event in sv and en counts as two cards. Machine translation creates a whole new card.

### B. JSONB column on the card

`card(id, year, category_id, text jsonb)` with `{"sv": "…", "en": "…"}`.

- Pros: one row per event, so identity, year and category stay single-sourced. Adding a locale needs no schema change. Postgres recommends `jsonb` over `json` for most uses, and GIN or expression indexes support `?` / `@>` queries such as "has an `en` text" ([PostgreSQL §8.14](https://www.postgresql.org/docs/current/datatype-json.html)).
- Cons: per-translation metadata (machine vs reviewed, translated_by, updated_at for the audit log) has to be nested in the JSON. Postgres notes that "any update acquires a row-level lock on the whole row" and that documents should be "an atomic datum". Translations edited independently by different admins are not atomic in that sense. Integrity (allowed locale keys, non-empty text) has to come from CHECK constraints or app code.

### C. Base table plus translation table (recommended)

`card(id, year, category_id, source_url, created_at, …)` and `card_translation(card_id, locale, text, status ['machine'|'reviewed'], updated_by, updated_at, PRIMARY KEY (card_id, locale))`. Use the same shape for `category` and `category_translation`, since category names are admin-editable too.

- Pros: one card identity across languages, so dealing and no-repeat logic, future voting, difficulty stats and highscores all key on `card.id`. Each translation row carries its own status and audit fields, which fits "AI translate, then a human reviews" and the admin audit log. Dealing is a plain join: `card JOIN card_translation ON locale = :game_locale`. Adding Norwegian is just adding rows. This is a normalised relational design and works on any SQL backend.
- Cons: an extra join and a slightly more involved admin form, which are minor at this scale.

**Recommendation:** C for cards and categories. B is the fallback if the backend choice (separate ticket) makes joins awkward. Avoid A, because it breaks card identity, which later features depend on.

## Decisions for the map / follow-ups

1. UI i18n: Paraglide JS v2 with the `['cookie', 'preferredLanguage', 'baseLocale']` strategy and no locale in URLs.
2. The server sends codes, and the client localises. Card text is content in the game's card language.
3. Card language is a game setting (default: host's UI locale). The deck is filtered by available translations.
4. Card data model: base table plus translation table with a `status` per translation (feeds *Card data model*). Update the GLOSSARY "Card" definition, since language belongs to a card's text, not to the card.
5. Open: `baseLocale` (sv or en), and whether a mid-game language switch is in v1 (it determines reload vs `reload: false` on a CSR game route).
